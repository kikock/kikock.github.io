一、为什么会有 Fake-IP？（解决什么根本痛点）

在早期传统的代理客户端中，普遍采用的是 Redir-Host 模式：

  1. 致命的握手时延：浏览器想要访问 google.com，本地必须先通过公网发起一次真正的 DNS 解析。即便通过代理查远端 DNS，也必须先承担一个完整的跨国 RTT（200~400ms）才能拿到真实 IP 开始建立连接。
  2. 严重的 DNS 泄露与污染：如果向本地运营商发起解析，访问的目标网站明文瞬间在本地宽带被记录，并极易遭遇投毒阻断。
  3. 域名丢失：当应用程序拿到真实 IP 发出网络包后，网卡上只有四层目标 IP，原始域名丢失，代理软件只能吃力地依赖反向域名嗅探（Sniffing）。

Fake-IP 的颠覆性设计哲学：【假 IP 换真时效，延迟真实解析】

  • Clash 在本机直接充当首选 DNS 服务器。
  • 任何应用来查 DNS 时，Clash 根本不向公网发出任何查询包，而是直接从保留网段 198.18.0.0/16 抓取一个未占用的假 IP（如 198.18.1.144），并在本地内存构建映射字典：
    $$\text{198.18.1.144} \longleftrightarrow \text{870306666.xyz}$$
  • 这一过程完全发生在本地内存中，耗时通常小于 0.5 毫秒！

三、为什么 nslookup 会报错？

  1. TUN 驱动的全局劫持：开启 TUN 模式后，虚拟网卡抓取全机 0.0.0.0/0 的全部出站数据包。即使你显式指定 nslookup 870306666.xyz 223.5.5.5，该数据包也根本飞不出物理网卡，而是被 TUN 驱动塞进了 Clash。
  2. 标准应用 vs 专用诊断工具：
    • 浏览器、curl、微信等调用的是标准系统 Socket API（getaddrinfo），拿到假 IP 后顺畅通过 TUN 与 Clash 完成还原；
    • nslookup 属于底层网络诊断工具，它跳过系统 API 自己构造原生 Raw DNS 报文，对报文头部的权威应答标志（AA/RA Flags）有极其严苛的校验，遇到拦截代理环境容易因格式差异抛出 Server failed。

四、Fake-IP 是如何彻底根治 DNS 泄露的？

很多用户常问：“我的本地宽带运营商能不能知道我访问了哪些境外网站？”
在 Fake-IP 模式下，DNS 泄露在物理逻辑上被彻底扼杀：

  1. 本地发包量为 0：在访问境外域名时，本地电脑根本没有向外界发送任何 DNS 数据包，运营商抓包结果为 0。
  2. 代理协议远端代查 (Remote DNS)：流量送入 Shadowsocks / Trojan / Hysteria2 / TUIC 时，Clash 打包的是原始域名字符串（DOMAINNAME）。整个数据包通过 TLS 高强度加密飞向海外 VPS，由海外服务器在境外出口完成真实解析。
  3. 4 大防泄露黄金配置：
    • no-resolve 参数：在 IP 规则上加上 GEOIP,LAN,DIRECT,no-resolve，避免规则匹配时在本地提前触发真实解析；
    • **ipv6: false**：坚决关闭 IPv6 解析，彻底堵死国内宽带运营商通过 IPv6 旁路窃取明文 DNS 的后门；
    • nameserver-policy + DoH：国内直连域名走加密的 https://dns.alidns.com/dns-query，全程运行在 HTTPS 443 密文中，旁路无法窥探；
    • 兜底规则走代理：配置末尾保持 MATCH,🌍选择代理节点，未命中域名的流量统一加密出海。

七、总结与最佳实践

  1. 认准真假 IP：在开启 Fake-IP 后，nslookup 查到 198.18.x.x 是完全符合协议设计的正常行为，不需要惊慌。
  2. **切勿在 Windows 强行监听 :53**：在 TUN 模式下，将监听端口改为 1053，依靠 TUN 驱动从内核层转发，是兼顾稳定性与权限的最优实践。
  3. 保持 DNS 覆写关闭：如客户端长图顶部提示所言，直接以维护良好的订阅 YAML 文件为准运行，既能保证节点订阅动态更新，又不会产生未知的配置覆盖冲突。
